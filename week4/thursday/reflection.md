## Question 1: Ansible vs Bash Idempotency

In Week 3, my Bash provisioning script achieved idempotency by using guard conditions before making changes. For example, `id kk-api >/dev/null || useradd kk-api` only created the user if it did not already exist. In Week 4, Ansible handled this automatically through idempotent modules. When the `ansible.builtin.user` module runs with `state: present`, it checks whether the user already exists and whether its properties match the desired configuration. If everything already matches, the task reports `ok` instead of making changes. If I had used `ansible.builtin.shell: useradd kk-api`, Ansible would execute the command every run, causing errors because the user already exists. The shell module does not understand system state, so it cannot determine whether a change is required. For provisioning tasks, idempotent modules are preferred because they compare the desired state with the current state before acting.

## Question 2: Handler Behaviour Under Parallel Execution

Handlers are only executed on hosts where a notifying task reports a change. If the systemd unit template changes on hosts A and B but not on host C, the `Restart service` handler runs once on host A and once on host B, but it does not run on host C. If two different tasks both notify the same handler on the same host, the handler still runs only once at the end of the play. Ansible automatically deduplicates handler notifications during a playbook run. This behaviour prevents unnecessary service restarts when multiple configuration files are updated together. Instead of restarting the service after every change, Ansible waits until all relevant tasks have completed and performs a single restart, making deployments more efficient and reducing service interruptions.

## Question 3: The Terraform to Ansible Inventory Bridge

Creating the inventory manually from `terraform output` worked for this lab, but it becomes difficult to maintain as infrastructure changes. One automation approach is to generate the inventory directly from the Terraform state or outputs using a script or tools such as `terraform output -json`. This keeps the inventory synchronized with the deployed infrastructure but depends on access to the Terraform state. Another approach is to use Ansible's AWS dynamic inventory plugin, which queries the AWS API and discovers EC2 instances automatically based on tags. This removes the dependency on Terraform state and always reflects the current cloud environment, but it requires additional AWS permissions and configuration. For the three-person KijaniKiosk team, I would recommend using Terraform outputs because it is simpler to implement, easier to understand, and integrates naturally with the existing workflow.

## Question 4: Configuration Drift in the Ansible Model

In Ansible, drift detection occurs only when the playbook is executed. During each run, Ansible compares the current configuration with the desired configuration defined in the playbook. If an engineer manually changes the UFW rules on the payments server, the next playbook run detects that the firewall configuration differs from the declared state and reapplies the correct rules. Unlike Terraform, Ansible does not provide a separate planning phase that automatically reports infrastructure drift before making changes. Terraform's `plan` command compares the real infrastructure with the state file and reports differences without modifying resources. Ansible focuses on convergence rather than independent drift reporting. This means the KijaniKiosk team should run playbooks regularly or integrate them into CI/CD pipelines so that configuration drift is detected and corrected as part of routine operations.
